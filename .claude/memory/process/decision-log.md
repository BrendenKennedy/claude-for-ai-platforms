# Process decision log

> Append-only, per `PROCESS.md` §3.1 / T3 and the `governance` record protocol. Process-level
> decisions land here: scope cuts and promotions, metric choice, kill/pivot calls, thresholds picked
> at gate reviews. Domain-specific judgment calls (data licensing, model release, security) go in
> that domain's log under `.claude/memory/policy/` instead.

| Date | Decision | Alternatives considered | Rationale |
|------|----------|-------------------------|-----------|
| 2026-07-25 | **Un-park Kubernetes.** It is now the orchestration spine: a `kubernetes` skill, `policy-as-code`, k8s templates, a manifest guard hook, and `platform-security.md`. | Keep Compose-only (the parent's position); support k8s as docs without tooling. | The parent scaffold parked k8s deliberately — "orchestration is a platform decision, not a scaffold one" — which was right for a DS scaffold where orchestration is incidental. It is wrong for an AI-platform scaffold, where the cluster *is* the substrate and most of `platform-security.md` is meaningless without one. Recorded rather than performed silently because the original decision was reasoned. Service mesh stays parked. |
| 2026-07-25 | **Policy canon may cite framework control ids.** Canon carries `[LLM01]`, `[ASI06]`, `[CIS 5.2]`; the framework text lives in `policy/frameworks/`. | Keep the parent's zero-citation convention ("methodology cites lineage; policy asserts rules"); or inline full citations with URLs in canon. | The user's requirement was that supporting framework documentation live in the policy section, and the fork's value proposition is that rules are *sourced* rather than invented. Zero citations made that unverifiable; inline citations would turn canon into citation soup and duplicate a moving external source. Ids-only keeps canon readable, and `check-scaffold.sh` check 8 fails on a citation that resolves to nothing. |
| 2026-07-25 | **`skillListingBudgetFraction` 0.02 → 0.04.** | Keep 0.02 and ship fewer always-on skills; or gate the security spine. | The fork adds 5 always-on skills and defaults ~11 gated ones on for a platform lane — ~28 live descriptions, which truncates at 2%. Gating the security spine was rejected: a scaffold whose selling point is "drop it in and the agent-security defaults are right" cannot have `agent-security` off by default. `/intake` turning off unused lanes is the pressure valve, and it reports what it turned off. |
| 2026-07-25 | **Phase numbers and names kept unchanged** (P1 Problem Definition … P7 Monitoring), with security added as a track (§3.9) rather than by renaming phases. | Rename to Problem & Threat Framing / Build & Harden / Evaluate & Red-Team etc., as originally planned. | The lifecycle was already archetype-agnostic, and every skill cross-references phases by number *and* name. Renaming would have created drift across ~50 files for presentational gain. The security track achieves the same outcome — items on every gate — without the churn. |
| 2026-07-25 | **`workflow-orchestration` is a new skill, not a replacement for `pipelines`.** | Extend `pipelines` to cover Airflow/Dagster/Temporal; or rename it. | They are different domains that share a word. `pipelines` is about ML *cascade seams* — one model's output feeding the next, where the failures live in the contract between stages. `workflow-orchestration` is about the *engine* that schedules and runs jobs, where the failures are idempotency, backfills, and an executor holding every credential in the system. Merging them would produce one skill whose description cannot route correctly for either. Both blockquotes name the other explicitly so the split is discoverable. |
| 2026-07-25 | **Allow-list entries are scoped to subcommands; `semgrep` and `helm template` are not allow-listed at all.** | Keep bare tool names for convenience; or add a hook to inspect flags. | A permission prefix cannot exclude a later flag, so `semgrep scan --autofix` and `helm template --post-renderer` are reachable under any prefix that permits the tool. A hook inspecting flags would be a guardrail where a permission is the boundary — the wrong layer (`security.md` S1). Removing them costs a permission prompt, not a capability. |
| 2026-07-25 | **The allow-list rule, generalised and written into `settings.json`: an entry stays only if it is non-mutating under _every_ flag it accepts.** Applied a second pass: `checkov`, `terraform plan`, and `tofu plan` removed entirely (joining `semgrep` and `helm template`); `syft` → `syft scan`; `gitleaks` → `gitleaks detect --redact`; `trivy` → `image\|fs\|config`; `conftest` → `test\|verify`. | Scope each of the removed tools to a subcommand like the others; or keep them and rely on the deny list. | The removed four have no safe prefix: `checkov --external-checks-git` clones a repo and imports its Python, and `terraform plan` evaluates `data "external"` (runs a local program) and loads provider binaries — so the widely-held belief that `plan` is read-only is false in a repo with attacker-authored `.tf`. A subcommand scope cannot exclude those flags because they attach to the same subcommand. The deny list is a floor, not a substitute — it enumerates known-bad, and these are known-*dangerous-under-some-flag*, which is a different shape. Cost is a prompt per invocation; the previous state was a false claim in a comment, which is worse than a prompt. |
| 2026-07-26 | **Reverse the fork: the AI-platform work merges back into one repo, renamed `claude-for-ml-platforms`, with the family chosen at `/intake`.** | Ship two repos with `upstream` kept pullable (the plan that was one command from executing); keep one repo but under the old `claude-for-datascience` name. | The fork was a superset, not a divergence — `/intake` already classified into two families and already flipped `skillOverrides` per lane, so the "ask what you're building" machinery existed. Against that, 65 of 107 inherited files were untouched: a split meant maintaining them twice forever, and the `check-scaffold.sh` exit-status bug (found in the fork, present in the parent) was a live example of the cherry-picking tax. The rename because ~60% of the tree is now platform/security and `claude-for-datascience` misdescribes it to anyone discovering it; GitHub redirects the old URL and this repo has renamed once before. |
| 2026-07-26 | **Both wings gate: always-on drops from 17 skills to the 5-skill chassis.** The security/platform spine and the DS core are now archetype-gated; `skillListingBudgetFraction` 0.04 → 0.03. | Keep the spine always-on and gate only the DS core; keep everything always-on and accept the budget. | Unifying two families into one repo makes an always-on set the *union* of both, which taxes everyone for what they didn't pick — a tabular project carrying the agentic threat surface, an inference platform carrying `eda` and `notebooks`. Gating both wings is the only version where the merge is a net context win rather than a loss. The chassis stays because `process`/`governance`/`testing`/`memory`/`wave-planning` are how the scaffold operates at all, in either family. |
| 2026-07-26 | **`agent-security` is gated on "is there an LLM or agent in this?" — a question asked separately from the archetype — rather than staying always-on.** | Keep it always-on (the 2026-07-25 position); gate it on the archetype like every other lane skill. | This reverses a decision made deliberately eight days earlier on the rationale that security defaults must not be opt-in, so it needs a reason rather than a shrug. The reason: **the skill was never the floor.** The floor is the hooks (always on, zero context) plus the canon (on-demand) — both hold regardless of profile. Gating on the *archetype* was rejected because the mapping is wrong in both directions: a "tabular" project that calls a model has an agentic surface, and an "inference platform" serving a classifier may not. The residual risk — a project that adds an agent later and never flips it on — is real and is mitigated by recording the answer in `project-definition.md` where `/gate` reads it, not by pretending it away. |
| 2026-07-26 | **The `PROCESS.md` §3.9 security track scales with archetype instead of applying uniformly, and `N/A — <archetype>` becomes a valid recorded gate answer.** | Keep one uniform track; drop the track entirely for model-building lanes. | A uniform track asks a cv project about cluster hardening and admission control, which is how a checklist loses legitimacy and starts getting routed around — the same failure the `secure-cicd` skill warns about for pipelines. Dropping it for model-building lanes was worse: those projects still have data provenance, leakage, PII, weight provenance, and a release decision. Three sizes, with the non-applicable items **written down as N/A** — because an item nobody considered is indistinguishable from one considered and dismissed, and only one of those is safe. |
| 2026-07-25 | **Guard hooks must reconstruct the post-edit file rather than scanning the hunk, and `check-hooks.py` must cover every tool path a hook is wired to — not merely every hook.** | Gate the guards on `Write` only and document the limitation; or have the guards ask on any `Edit` they cannot resolve. | Scanning a hunk meant `guard-k8s-manifests.py` and `guard-agent-config.py` skipped every check on `Edit`, which is how manifests and settings are actually changed — the guards were green for the life of the fork because all 56 test cases used `Write`. Documenting the limitation was rejected: a guard that silently does nothing is worse than no guard, because it is counted. Asking on every unresolvable `Edit` is retained only as the *fallback* in `guard-agent-config.py`, where fail-open on a self-widening check is the wrong direction; elsewhere reconstruction succeeds and a blanket ask would train the user to click through. Coverage is now counted in tool paths, not case totals. |
