# NIST SP 800-190 — Application Container Security Guide

**Identity:** NIST · SP 800-190 (September 2017) · https://csrc.nist.gov/pubs/sp/800/190/final
**Verified:** 2026-07-25. Still the current revision — **no Rev. 1 published**. Nine years old; its
risk *decomposition* remains the standard reference, its tooling and orchestrator specifics do not.
**Canon citing it:** `platform-security.md` (P2, P4) · `supply-chain.md` (C5)

> The document that established how to think about container security by splitting the problem into
> five tiers — image, registry, orchestrator, container, host OS — each with its own risks and
> countermeasures. We carry it for that decomposition, which is still how threat models for
> containerised systems are organised, and for its authority in compliance mappings.

## The risk decomposition

| Tier | Representative risks |
|---|---|
| **Image** | Vulnerabilities in packaged software; embedded secrets; untrusted or unverified base images; configuration defects; malware |
| **Registry** | Insecure connections to the registry; stale images with known CVEs; insufficient authentication and authorization on push/pull |
| **Orchestrator** | Unbounded administrative access; unauthorized access to the cluster; poorly separated inter-container network traffic; mixing workload sensitivity levels on a host; orchestrator node trust |
| **Container** | Runtime software vulnerabilities; unbounded network access from containers; insecure container runtime configuration; app vulnerabilities; rogue containers |
| **Host OS** | Large attack surface; shared kernel; host OS component vulnerabilities; improper user access rights; host filesystem tampering |

Its countermeasures fall into recognisable families: image scanning and signing, registry access
control and image lifecycle policy, orchestrator least-privilege and workload separation, runtime
confinement and least-privilege execution, and container-specific host operating systems.

## What we adopt

- **The five-tier decomposition as threat-model structure.** `/threat-model` uses it for any
  containerised component: a threat model that only considers the application code and skips the
  registry and host tiers has a predictable blind spot.
- **"Mixing sensitivity levels on a host is a risk"** → canon `P10` (tenancy boundaries are enforced,
  not assumed) and the scheduling guidance in `kubernetes`.
- **Image-tier risks** → `C5` (base images pinned by digest, rebuilt on CVE) and `P4` (images pinned
  and from an approved registry).
- **"Containers share a kernel"** as the standing argument for why `P2` (no host namespace access)
  and PSS `restricted` are non-negotiable — the isolation boundary is thinner than a VM's, so the
  configuration has to do more work.

## What we leave

- **Its orchestrator guidance as specifics.** Written before Kubernetes settled; superseded by
  `cis-kubernetes.md`, `nsa-cisa-k8s-hardening.md`, and `k8s-pod-security-standards.md`. Where they
  disagree, they win.
- **Container-specific-OS recommendations.** Sound, but a platform choice most projects don't make.
- **Its tooling landscape.** Nine years stale; `supply-chain-security` carries current tools.

## Gotcha

Cite this for **structure and for compliance crosswalks**, not for configuration. Its age is the
whole caveat: a 2017 document cannot tell you what a 2026 pod spec should contain, and treating it
as though it can produces guidance that is confidently out of date.
