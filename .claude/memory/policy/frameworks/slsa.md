# SLSA — Supply-chain Levels for Software Artifacts

**Identity:** OpenSSF · **v1.2** current (v1.0 released April 2023) · https://slsa.dev/spec/
**Verified:** 2026-07-25. v1.2 reported as the current specification version; the Build Track is
stable and the Source Track remains under development. Confirm the exact minor version at the
publisher before citing it in an attestation policy.
**Canon citing it:** `supply-chain.md` (C3, C4, C6)

> The maturity ladder for "can you prove where this artifact came from?" — expressed as build levels
> with concrete requirements, plus a provenance format that tooling actually emits. We carry it
> because it converts an unbounded worry (supply chain) into a small number of achievable steps.

## The build levels

Cumulative — each level includes the previous:

| Level | Requirement | What it buys |
|---|---|---|
| **L0** | No guarantees | The default state. Named so it can be talked about. |
| **L1** | Provenance exists: the build produces a signed record of source repo, commit, build inputs, and a digest of the output | You can answer "what built this?" — stops the most casual substitution |
| **L2** | Provenance is generated by a **hosted build platform** and signed by it, not by the build script | The provenance can't be forged by whoever controls the build definition |
| **L3** | Hardened build platform: builds are isolated from each other, the signing key is inaccessible to build steps, provenance is non-falsifiable | Resists a compromised build *tenant*, which is the realistic supply-chain attack |

The specification is deliberately narrow: it addresses **build integrity**. It does not claim to
cover dependency vulnerability, code quality, or whether the source itself is malicious.

## The provenance format

SLSA provenance is emitted as an **in-toto attestation** (ITE-6): a signed envelope binding a subject
(the artifact digest) to a predicate (how it was built). The ecosystem that produces and verifies it:

| Tool | Role |
|---|---|
| **cosign** (Sigstore) | Signs and verifies artifacts and attestations |
| **Fulcio** (Sigstore) | Issues short-lived signing certificates from an OIDC identity — no long-lived signing keys |
| **Rekor** (Sigstore) | Transparency log recording signing events, so a signature can't be quietly issued |
| **in-toto** | The attestation envelope format SLSA provenance rides in |
| **slsa-github-generator**, GitHub artifact attestations | Produce L2-conformant provenance from a hosted CI platform |

Keyless signing via Fulcio is the part worth internalising: the identity doing the signing is the
CI workflow's OIDC identity, so there is no signing key to steal or rotate.

## What we adopt

- **Build L2 as the minimum for anything we ship, L3 for anything that reaches production**
  (canon `C4`). L2 is genuinely reachable on hosted CI with existing tooling; setting the floor lower
  produces provenance that the build script itself could have forged.
- **Sign on build, verify on run** (`C3`). Signing without verification is theatre — the verification
  step is the control, and it belongs at admission (`policy-as-code`) as well as in CI.
- **Keyless signing via Fulcio + Rekor.** No long-lived signing keys is the same principle as `I3`
  (no static workload credentials), applied to the build.
- **Provenance covers model artifacts too** (`C7`). A fine-tuned checkpoint is a build output; it
  gets the same attestation treatment as a container image. This is the extension the AI platform
  case needs and that SLSA does not itself discuss.

## What we leave

- **Levels beyond the current Build Track.** L4-era aspirations from the pre-1.0 drafts are not part
  of the current specification; we do not gate on requirements the spec no longer defines.
- **The Source Track**, until it stabilises — we adopt the source-review discipline through code
  review and branch protection instead, without claiming a SLSA source level.
- **Any claim of a SLSA level without an attestation to show.** The level is the artifact, not the
  intention. `control-coverage.md` records the level actually achieved and how it was verified.

## Gotcha

**SLSA proves the build, not the goodness of what was built.** An L3 attestation on a container full
of vulnerable dependencies is an honest, verifiable record of a bad artifact. It composes with — and
does not substitute for — SBOM (`sbom-formats.md`) and vulnerability scanning. Teams that reach L3
and stop have secured the wrong half.
